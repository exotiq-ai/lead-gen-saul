# Exotiq partner intake — approved implementation scope

## Scope and privacy
This release adds operational provenance and sales coordination only. No private agreement text, commission terms, financial eligibility engine, sending automation, or payments belong in this repository or sales UI. Existing source/assignment/activity fields must not be overwritten by baseline labeling. User will confirm baseline/intake policy with partner separately. Review confirmation is an operational record, not financial entitlement.

## Architecture lock
- Existing Next.js 16 + Supabase service-side API and admin email allowlist remain.
- A restricted authenticated partner workspace at `/sales` titled My Leads, with Add Operator; admin management/review at `/dashboard/team`.
- Existing admin auth helper remains admin-only. New sales auth helper admits verified-email active Exotiq sales members and existing admins. Partner users cannot access legacy dashboard/API routes, other tenants, exports, secrets or founder correspondence. Individual email logins, no shared credentials. Admin preregisters emails; no unsolicited invites.
- Exotiq tenant constant `00000000-0000-0000-0000-000000000001`; server-derived tenant, member, team, actor. New tables service-role only with RLS and denied anon/authenticated privileges. Verify legacy direct REST grants cannot bypass app boundary before allowing reps.
- UI reference lock: existing dashboard tokens/components, compact white/light Exotiq context where current theme applies; no redesign. Preserve typography, border, CTA semantics. Accessible labeled inputs, keyboard focus, mobile stacking, explicit retry/errors, no financial fields.

## Shared API contract (backend owner implements routes; parent provides auth)
Parent creates `src/lib/sales/auth.ts` exporting `requireSalesActor(req: NextRequest): Promise<{actor: SalesActor,response: NextResponse} | {error: NextResponse}>`. `SalesActor` in `src/lib/sales/types.ts`: `{userId:string,email:string,displayName:string,isAdmin:boolean,memberId:string|null,team:string|null,tenantId:string}`. Response carries any auth cookie changes. Backend must check `error` and use returned response cookies or no-store response helper. Admin enforcement in each route, not just proxy.

Endpoints, all no-store:
- GET `/api/sales/workspace` => `{actor,members: SalesMember[],registrations: SalesRegistration[],accounts: SalesAccount[],baselines: BaselineSummary[]}`. Admin sees review queue + all accounts; rep sees own submissions and assigned accounts only. Limit/paginate or bounded returned summaries explicitly, never silently truncate. No general lead metadata/history on reps. Members exposed to reps limited to themselves. Baseline summary admin-only.
- POST `/api/sales/registrations` => `{registration}`. Body `{request_id:uuid,company_name,email?,phone?,website?,contact_name?,relationship_note?}`. Require name and >=1 usable contact identifier; identity matching before create, deterministic normalization; no crawler/sends. Persist server actor/time, append immutable submitted event. No canonical lead is inserted until accepted. Match current tenant leads and pending/accepted submissions; possible company-name match goes review, not auto-merge. Match info for reps only generic classification, no other contact details.
- POST `/api/sales/registrations/[id]/review` admin-only => `{registration}`. Body `{decision:'accepted'|'declined',reason:string,lead_id?:uuid,assigned_member_id?:uuid}`. Transaction: lock tenant, recheck matches/current state, require explicit existing lead selection for matches, never create duplicate for identical pending submissions. If accepted no existing match, insert one minimally populated canonical lead source `partner_submission`; preserve all prior data on existing lead. Do not steal existing owner; assignment to an already-owned account requires dedicated explicit handoff. Events contain actor/time/prior/new state. Re-review must be safe/conflict not overwrite.
- POST `/api/sales/members` admin-only => `{member}` body `{email,display_name,team:'starr'}`. Preapprove a login; no email sent. PATCH `/api/sales/members/[id]` admin-only `{active:boolean}`. No email reassignment.
- PATCH `/api/sales/accounts/[leadId]` => `{account}`. Rep may update own assigned account's next_action,next_action_due_at and append outcome_note only; admin may also explicitly assign member or unassign with reason. Never changes original source, registration decision or financial attribution. Append event for assignment and notes; no lead_activities score-side-effects required.

## Data contract
Use new additive migration `015_partner_sales_registry.sql`. New tables `sales_members`, `sales_registrations`, `sales_registration_events`, `sales_account_assignments`, `sales_baseline_snapshots`, `sales_baseline_accounts`. UUID IDs, tenant-scoped constraints/FKs, database timestamps. Members email unique normalized; active flag. Baseline membership does not imply rights or overwrite original source. Baseline files and raw data remain PRIVATE outside git. RPCs service-role only for atomic submit/review/account updates. Serialization/idempotency required, not just a UI duplicate warning.

`SalesRegistration`: id,company_name,contact_name,email,phone,website,relationship_note,submitted_at,status(pending|accepted|declined),match_kind(none|existing|submission|possible),lead_id|null,submitted_by_member_id|null,submitted_by_name,reviewed_at|null,decision_reason|null,events (safe own receipt history). Rep responses omit candidate IDs/business/contact/history that belong to another member. Own submitted input remains visible.
`SalesMember`: id,email,display_name,team,active.
`SalesAccount`: lead_id,company_name,contact_name,email,phone,website,status,assigned_member_id,assigned_name,source_label,next_action,next_action_due_at,updated_at. Source label operational: Exotiq existing / Partner submitted / Review source. Rep view only approved assigned operational fields, not score_breakdown or founder notes.
`BaselineSummary`: id,captured_at,lead_count,exception_count,manifest_sha256 (no raw data/file URL).
